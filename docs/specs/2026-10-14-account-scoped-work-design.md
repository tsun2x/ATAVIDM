# Account-Scoped Videos, Results, and Reports Design

**Date:** 2026-10-14  
**Status:** Approved direction; awaiting written-spec review  
**Scope:** Per-account visibility for uploaded videos and derived results, with shared access to completed reports under the existing Reports role gate.

## User-visible behavior

- Enforcers see their own uploaded videos and results derived from those videos. The ownership boundary applies wherever those records are listed or fetched, including the Live Monitor upload history, Violations, Review Queue, Motorcycle Detail Review, and the user-facing dashboard and analytics aggregates.
- Administrators retain system-wide access and can filter video/result views and reports by uploader/account.
- Existing viewer permissions do not change. Viewers remain read-only and do not gain Reports access.
- Reports remains available to the roles that can access it today (enforcers and administrators). An enforcer can generate a report from their own uploaded-video results. Administrators can generate reports across all accounts or for a selected account.
- Completed report history and downloads are shared among users who already have Reports access. Provide a “My Reports / All Completed” filter; “My Reports” filters by the report's `generated_by` value.
- Live-camera streams and records that have no uploaded-video owner remain system-level/shared. They are not assigned to an account by inference.

## Ownership and data boundaries

The existing schema has `videos.uploaded_by` and `reports.generated_by`. Result records are scoped through their direct `video_id` relationship to `videos.uploaded_by`; no timestamp, filename, processing order, or other indirect clue establishes ownership. A source-less record (including a live-camera record) remains system-level/shared under the existing role checks. A record linked to a video with a NULL `uploaded_by` is visible only to administrators in user-scoped pages and filters; its owner is not backfilled or guessed.

For enforcers, server-side authorization and query filtering must apply to list APIs and direct-object routes, not only UI filters. An enforcer must not be able to retrieve another account's source video, evidence/media, result detail, review item, or report input by changing an ID or query parameter. Administrator access remains system-wide. Completed report artifacts remain downloadable by any account that already has Reports permission, as chosen by the user.

## Report generation and history

The existing report-history row is written after artifact generation succeeds, so report history represents completed reports. Preserve that behavior. Enforcer report queries are constrained to violations/results whose source video belongs to that enforcer. Administrator queries may include all owners or a selected owner. Generated report history is shared among Reports-authorized users, with the selected filter controlling whether the list shows reports generated by the current user or all completed reports.

## Storage and compatibility

No database schema change or ownership backfill is expected: the needed direct ownership columns and result-to-video relationship already exist. Implementation should use joins/filters against these fields and preserve existing API shapes, SQLite schema, role names, and report-generation behavior. Existing NULL-owner rows are handled as described above. If implementation inspection discovers an endpoint whose data cannot be safely scoped using the current direct relationships, stop and report that a schema change may be needed before adding guessed ownership.

## Failure and edge behavior

- Missing, deleted, or NULL-owner source ownership never grants an enforcer access; administrator access follows current administrator permissions.
- Unauthorized cross-account object requests use the app's existing not-found/forbidden response convention without revealing another account's record contents.
- Empty “My” views show a normal empty state. Admin account filters may include an all-accounts option.
- Live-camera/source-less records retain their current shared visibility and role checks; they are not included in an enforcer's uploaded-video-only report scope unless the existing report flow explicitly selects system-level data. This boundary must be preserved consistently in report filters.

## Verification expectations for the later implementation plan

Focused checks should cover two enforcers and an administrator: each enforcer sees their own uploaded videos and video-derived results, cannot fetch the other's media/evidence/detail or include the other's results in a generated report, and can see/download completed reports generated by either account; the administrator can see and filter both accounts; NULL-owner data stays out of enforcer-owned views; and source-less/live-camera behavior remains unchanged. Check that report history contains only successful completed report generation and that no schema migration or ownership backfill is introduced.
