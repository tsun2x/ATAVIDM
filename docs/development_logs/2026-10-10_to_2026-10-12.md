### Detailed Changes

- Added role defaults and per-user effective capability views for case confirmation, notice-print attestation, policy proposal and approval, plate verification, event-time confirmation, and the separate administrator-only plate-identity confirmation action.
- Added administrator controls for the six fixed legal-policy grants. Request bodies accept only `grants` and `revokes`; unsupported permission names, forged actor fields, duplicate or contradictory changes, invalid reasons, and self-grants are rejected before any write.
- Added an atomic SQLite update operation. It rechecks that the actor is an active System Administrator while holding the write lock, records grant reason and granter, and soft-revokes grants using the existing `revoked_at` field.
- Preserved role-derived permissions after explicit grant revocation. Inactive accounts have no effective capabilities even when grants remain recorded.
- Changed case confirmation, notice-print attestation, event-time confirmation, and policy proposal routes to authenticate first and rely on their existing service/database authority checks. Explicit supported grants can now reach those checks; role status alone still cannot approve legal policy or confirm plate identity.
- Changed review queue, review-decision history, and motorcycle-detail list APIs to use the same Admin/Enforcer restriction as their pages and evidence routes.
- Kept the account system local and admin-managed; no public registration, new role, duty scheduler, database migration, or package dependency was added.

---

### Technical Explanation

The Flask route derives the acting user ID from `auth.current_user()` and never accepts an actor ID from the request. The SQLite adapter independently validates that actor as an active administrator and uses `BEGIN IMMEDIATE` so validation and mutation are serialized. Effective legal authority continues to come from the existing `can_*` functions, which re-read the active user and stored permissions on each request. The grant API is limited to the existing schema CHECK list.

---

### Code Impact

The Settings page now makes the current role and legal capability model visible. Existing account creation and role editing remain in place. The new access API is admin-only. Existing case, print, policy, and event-time services remain authoritative for protected mutations; route decorators no longer block a valid explicit capability before those checks run.

---

### Database Changes

None. Grant records use the existing `policy_permission_assignments` table. The schema has a grant actor field and revocation timestamp but no revocation actor field, so revoke time persists while the revoking administrator is not recorded in that table.

## 2026-10-10 00:53 — Fix account-access modal request races

### Objective

Correct the two reproduced Settings access-modal defects: asynchronous responses could display one account's capabilities under another account's title, and the modal exposed a grant/revoke control for the administrator-only `confirm_plate_identity` action.

### Summary

Bound each modal selection and its responses to an account ID and monotonically increasing generation. Old GET and PUT responses and errors are ignored after selection changes or modal closure; a pending write retains its original URL target and failure messaging asks the administrator to reopen the account to check state. Only the six API-supported legal permissions receive grant/revoke controls.

### Files Modified

  - Records this follow-up and its verification results.

### Detailed Changes

- A modal selection owns a request generation and immutable account ID. A newer selection or the modal's `hidden.bs.modal` event invalidates earlier callbacks.

## 2026-10-10 01:15 — Serialize account-access permission writes

### Objective

Prevent overlapping permission writes in one account-access modal from saving multiple changes while leaving the displayed capabilities stale.

### Summary

Permission controls are now serialized for the selected account: submitting one change disables all six grant/revoke controls until a fresh access response is loaded. Both successful writes and failed or uncertain writes trigger a GET for the same account and modal generation. A regression test reproduces the previous detached-button response loss and verifies the serialized flow, authoritative refresh, and recovery after a failed operation.

### Files Modified

#### Created

None.

#### Modified

- `static/js/settings.js`
  - Locks all permission controls while a write and its authoritative refresh are pending; refreshes from the access API after success or failure; leaves the modal safe to reopen if the refresh itself fails.
- `tests/js/test_account_access_races.cjs`
  - Reproduces the overlapping-write defect and verifies serialized updates, exact request bodies/targets, final effective and explicit grant display, failure recovery, and pending-write invalidation on close/reopen.
- `docs/development_logs/2026-10-10_to_2026-10-12.md`
  - Records the v2 repair and verification.

### Detailed Changes

- The active account context tracks whether a permission update is pending. A write locks every permission control; additional clicks while locked dispatch no request.
- Once a PUT succeeds, the modal issues a fresh GET for the captured account and generation. It renders only that authoritative response and re-enables controls after the refresh succeeds, so the next permission change can start against current state.
- If a PUT fails or its result is uncertain, the modal still refreshes from the server. A successful refresh displays the current permissions, explains the uncertainty, and restores controls. If the refresh also fails, the stale panel is cleared and the administrator is instructed to close and reopen the account before trying again.
- Account switching and modal close/reopen continue to invalidate pending callbacks. A completed write is never redirected or retried for the newly selected account.
- The six supported permission actions and informational-only `confirm_plate_identity` row remain unchanged.

### Testing
