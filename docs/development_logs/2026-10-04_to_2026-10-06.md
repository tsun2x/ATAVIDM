## 2026-10-04 21:57 — Add visual trajectory overlays

### Objective

Show tracked vehicle paths during video processing and live monitoring so movement can be compared visually with saved lane and scene geometry, without changing detection or violation decisions.

### Summary

Added a Supervision `TraceAnnotator` adapter using ByteTrack IDs and bottom-center positions. Trace histories are isolated by TAVIDM identity epoch so reused track IDs do not inherit an earlier vehicle's path. Upload processing and live-monitor frames render traces over existing scene geometry; overlay construction or drawing failures fall back to rendering without traces. The overlay is visualization-only and does not affect rules, persistence, or model training.

## 2026-10-05 13:50 — Add trajectory-based traffic sign review candidates

### Objective

Extend the Disregarding Traffic Sign evaluator so configured No Left Turn, No Right Turn, No U-turn, and No Overtaking signs can raise pending review candidates from tracked movement. Human administrators retain final decision authority.

---

### Summary

Added turn-maneuver checks using a sign-associated lane flow arrow, a lane-associated threshold, and recent vehicle bottom-center trajectory. Added No Overtaking checks requiring two tracked vehicles to swap longitudinal order while moving with the configured flow inside the sign-associated lane geometry; a lane change without an observed pass does not raise a candidate. All emitted events use the existing review outcome; no schema, model, or automatic-confirmation changes were made. Generic signs remain informational because they have no defined maneuver semantics.

---

### Files Modified

#### Created

- `tests/test_traffic_sign_maneuver_rules.py`
  - Covers prohibited turns, stale trajectory rejection, bottom-center geometry, order-swap overtaking, and the video rule entrypoint.

#### Modified

- `core/violation_engine.py`
  - Adds the fail-closed turn and overtaking evaluators while preserving the existing No Entry path.
- `docs/development_logs/2026-10-04_to_2026-10-06.md`
  - Records this completed implementation and its verification.

---

### Detailed Changes

No Left Turn, No Right Turn, and No U-turn candidates require exactly one sign-associated lane flow and threshold geometry. A candidate requires a recent threshold crossing in the configured approach direction plus an outgoing path consistent with the prohibited maneuver. Trajectory samples older than the tracker motion window are ignored.

No Overtaking requires a sign-associated lane polygon and flow arrow, two currently tracked vehicles, forward movement by both, and a behind-to-ahead order reversal inside the lane geometry. Missing or ambiguous geometry fails closed with diagnostics. Generic signs still produce no candidate.

---

### Technical Explanation

The evaluator reuses the existing `TrackHistoryView`, scene annotation objects, lane-flow vectors, line intersection primitive, and review-event path. It compares movement in image coordinates against the explicit configured flow; it does not consume the visual Supervision trail renderer. Candidate generation remains separate from human confirmation.

---

### Code Impact

Uploaded-video and live processing already pass track history and the projected scene context into the shared rule engine, so both paths can evaluate these candidates when their scene annotations are configured.

## 2026-10-05 16:49 — Verify Plates from Pending Review Queue

### Objective

Allow an administrator to verify or correct the plate while reviewing a pending observation, then carry that human decision into the case/report after the violation is separately confirmed.

---

### Summary

Added an admin-only plate review action to the Review Queue evidence panel, including manual entry when OCR has no candidate. The selection is retained in the existing append-only case-action audit and appears when the queue item is reopened. Case materialization transfers the staged plate to the existing case verification fields; machine OCR remains only a candidate and cannot confirm either the plate or violation.

---

### Files Modified

#### Modified

- `tests/test_plate_ocr.py` — candidate transfer, retry, manual entry, and role coverage.

---

### Technical Explanation

Review-level plate choices use `case_action_events.review_id` with no schema changes. Candidate ids are resolved server-side against the review's manifest and crop evidence. Case confirmation transfers the saved choice through the existing `verify_plate_identity` path; idempotent retries do not duplicate the case verification event, and a later review does not overwrite an already verified case plate.

---

### Code Impact

The Review Queue API gained `POST /api/review-queue/<review_id>/plate`, restricted to active System Administrators. Case decision/materialization behavior is unchanged unless an admin has explicitly saved a plate choice for that review.
