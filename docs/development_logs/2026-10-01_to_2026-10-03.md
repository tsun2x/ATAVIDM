### Detailed Changes

The detail gate accepts only:

- `md-detail-3c-v1`: `0=helmet_nut_shell`, `1=helmet_acceptable`, `2=side_mirror` (identity prefix `md3c`)
- `md-detail-4c-v1`: the same three IDs plus `3=no_helmet` (identity prefix `md4c`)

`resolve_detail_contract()` requires readable contiguous IDs, exact names, count, and order, after the existing `detect` task check. Pilot, main-detector, mixed, reordered, missing, duplicate, and malformed maps are rejected with a visible reason. A rejected checkpoint reads no crop, builds no predictor, leaves the candidate queued, and spends no scan attempt.

A validated checkpoint stores its version, model kind, class map, and prefix on the checkpoint and in each saved scan. Class ID 3 decodes to `no_helmet` only for a four-class checkpoint. Inference results are checked against that map; out-of-range IDs fail the candidate.

`no_helmet` is associated only with the main detector’s rider head region. Another rider, truncated or unrecorded nearby riders, a missing rider, or a clipped box prevents a definite uncovered-head attribution. A helmet class and `no_helmet` on the same head, or contradictory states across selected frames, stay `ambiguous` and keep the observations. No detection remains `unknown`.

The review page and evidence modal use “Uncovered head observed” and state that it is not a confirmed violation. Ambiguous cases stay labeled ambiguous. There is still no detail confirm action.

---

### Technical Explanation

`check_detail_class_map()` still validates one roster. `load_detail_checkpoint()` calls `resolve_detail_contract()`, which tries the two rosters and reports the failure that matches the parsed length, or a structural failure (missing, malformed, non-contiguous, duplicate) independent of length. IDs are never relabeled.

`UltralyticsCropPredictor` continues to reject a result `names` map that differs from the validated tuple and class IDs outside that tuple. Mapped boxes are stored in source-frame coordinates with the raw label, confidence, class ID, contract, and `evidence_limited` flag. A `no_helmet` box that extends outside the scan image or touches the crop or source-frame edge is not a definite attribution.

Cross-frame reconciliation replaces the candidate helmet summary with `ambiguous` when selected frames have different definite helmet states, or when one frame is definite and another is ambiguous. A frame with no detection does not by itself override a definite frame.

Designation fingerprinting, model cache, retry limits, crash recovery, bounded batches, and one GPU reservation per batch are unchanged.

### Code Impact

## 2026-10-01 13:12 — Cross-frame helmet summary for motorcycle detail review

`attemptCompleted()` trusts `latest_attempt_status` when present, because the worker sets the in-memory job to `done` before `finish_processing_run()` writes `completed`. The old `video_status === "processed"` completion condition was removed.

A dismissed Obstruction item could then be linked to a case with a policy record (`decision=no_violation`, `creates_case=True`), and a confirmation could return the winning correction as success. Second, migration 013 ran its rebuild through `executescript()` without a transaction, so an interruption left `review_decisions__retained` or a half-built table on disk and the retry failed.

### Summary

Review decision and case writes now run under a SQLite write lock (`BEGIN IMMEDIATE`). The review, its saved decision, and the sibling group are re-read inside the lock. Any existing decision seen there goes to the existing retry-or-conflict comparison and never authorizes materialization. Migration 013 now runs as one explicit transaction, verifies the result before commit, and recovers the partial states the earlier code could leave. When both tables hold conflicting history, it stops with a diagnostic and changes nothing.

### Detailed Changes

- Defect A root cause: the existing-case path read decision state without a lock and treated "a decision exists" as permission to skip the attach. `_complete_materialization()` then linked every member of the stale group. Now every read that decides what to write happens inside `BEGIN IMMEDIATE`. A competing no-violation either commits before the lock (the confirmation then sees it and conflicts) or waits until the confirmation commits (and then conflicts itself).
- Defect B root cause: the confirmation read "no decision", a correction committed, and the non-pending recovery path recovered the correction's case. When `decision_insert` is given and any decision exists, the first locked stage raises `ReviewDecisionStateConflict`, and `_retry_or_conflict` returns 409 unless decision, selected rule, reason, and idempotency key all match.
- Fused siblings are confirmed and linked in the first-stage transaction. A no-violation or correction aimed at a sibling after that point conflicts ("closed and has no review decision") instead of being consumed.
- Completion and recovery rebuild the group under the lock. They take the policy version only from durable intent or snapshots, as before.
- Matching retries now report `idempotent_retry: true` when a duplicate lands inside the window.
- Migration 013 commits the caller's pending work, turns foreign keys off, checks that they are off, and runs `BEGIN IMMEDIATE`. Each statement goes through `conn.execute()`. Before commit it checks the row set, shape, five protections, and `PRAGMA foreign_key_check(review_decisions)`. On any failure it rolls back, turns foreign keys back on, and raises `MigrationError`.
- Recovery rules for a leftover `review_decisions__retained`:
  - If the live table is missing, the retained table is renamed into place.
  - If every retained row is present unchanged in the live table, the retained table is dropped with a logged warning.
  - If the live table is the migration-012 shape and every row in it is present unchanged in the retained table (the empty table migration 012 re-creates on restart), the live table is dropped and the retained table renamed.
  - Any other combination raises `MigrationError` listing the conflicting ids. Neither table is changed.
  - Missing indexes or triggers on a current-shape table are recreated.

### Technical Explanation

Decision rows are append-only and unique per review, so the only race is on the absence of a decision. One SQLite write lock around each read-then-write stage closes that window. Python's legacy transaction mode does not start a transaction for SELECT, which is why the earlier atomic helpers could read `pending` in autocommit mode while another connection committed. Savepoints keep each nested adapter helper all-or-nothing inside the shared transaction.

### Performance Notes

Each decision holds the database write lock for two short transactions. Other writers wait up to the SQLite busy timeout (5 seconds) instead of interleaving.

### Known Limitations

- A writer that waits longer than the 5-second busy timeout gets `sqlite3.OperationalError: database is locked`, which the routes do not translate to 409.
- The no-window race tests wait 1.5 seconds at the seam to prove a blocked competitor did not commit.

### Risks

Any future adapter helper called inside `review_write_transaction()` must not commit, call `executescript()`, or open its own connection.
