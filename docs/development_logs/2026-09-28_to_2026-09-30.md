## 2026-09-28 — Hybrid motorcycle detail-review workflow (implemented, not activated)

### Objective

Add a hybrid detail-review workflow for uploaded videos: group motorcycle
detections by track occurrence, keep at most two useful frames per occurrence,
run a queued second YOLOv8 pass over the padded crops, and present helmet and
side-mirror observations in a separate human-review queue — without ever
declaring, confirming, or creating a violation.

### Summary

New `core/motorcycle_detail.py` (selection + association) and
`core/motorcycle_detail_scan.py` (checkpoint gate + queued crop pass) were
wired into uploaded-video processing. A new additive table
`motorcycle_detail_candidates` (migration 011) stores one candidate per track
occurrence with its run-scoped evidence, scan state, observations, and human
outcome. New authenticated routes and a UI page expose the queue to enforcers.
The existing `review_queue`, its confirm/dismiss API, and the 12 canonical
violation types are unchanged, and the crop scan cannot reach the violation
engine.

## 2026-09-28 — Shared GPU reservation, occurrence bounds, and scan recovery

### Objective

Fix four review findings in the motorcycle detail workflow: a single shared GPU
reservation for every inference caller, motorcycle-only occurrence bounds,
spatial mirror attribution, and queued-scan/checkpoint-gate recovery after a
restart.

### Summary

`core/gpu_inference_slot.py` (new) is now the authoritative single-slot
reservation for the one GPU. The uploaded-video worker, background crop
batches, the manual `scan-now` batch, and every live camera frame take it in
turn, with strict priority (video job > crop batch > live frame) and FIFO within
a level. The video worker holds it for the whole job and re-queues at the queue
head when its bounded wait elapses; live frames never wait and are dropped.
`TrackOccurrenceRegistry` now bounds motorcycle and non-motorcycle occurrences
separately, so a frame of 24 cars can no longer evict the motorcycle under
review. Mirror attribution matches the target by spatial IoU, so a padded crop
re-detecting its own motorcycle is no longer mistaken for a second, overlapping
bike. The scanner refreshes a failed checkpoint gate by configuration
fingerprint, skips a batch without claiming when the device is busy, and
recovers `scanning` rows abandoned by a dead process at start-up. That
start-up recovery strictly precedes the scanner thread, and a broader
start-up pass is still permitted after an early stale-only pass, so the loop's
first batch can no longer consume the one-shot recovery and strand a row that a
just-dead process abandoned inside the stale window.

### Files Modified

- `core/gpu_inference_slot.py` (new) — priority/FIFO reservation with bounded
  waits, same-owner reentrancy, and introspection.
- `core/motorcycle_detail.py` — separate `max_active` / `max_foreign` budgets,
  bounded generation bookkeeping, spatial target matching for mirrors.
- `core/motorcycle_detail_scan.py` — reservation-bounded batches, queue peek
  before claim, checkpoint fingerprint + model cache stamp, start-up recovery.
- `app.py` — worker reservation, `_gpu_slot`, `_VIDEO_JOB_GPU_WAIT_SEC`,
  `_background_workers_allowed`, `bootstrap_detail_queue`, first-request
  bootstrap, manual `scan-now` 409 on a busy device.
- `core/live_stream.py` — per-frame non-blocking reservation with dropped-frame
  accounting.
- `database/sqlite_adapter.py`, `database/db.py`, `database/adapter_base.py` —
  `recover_stale_motorcycle_detail_scans(..., include_recent=False)` and
  `count_queued_motorcycle_detail_scans()`.

### Files Created (tests)

- `tests/test_gpu_inference_slot.py` — mutual exclusion, preemption, non-blocking
  live frames, release on exception, idempotent release, 10-thread contention.
- `tests/test_gpu_reservation_wiring.py` — video job holds and returns the
  device, release on failure, re-queue on timeout, bootstrap idempotency,
  reloader-parent opt-out, manual 409, live-frame drop.

### Database Changes

None. No table, column, index, or migration was added or altered; the two new
adapter methods read and update the existing `motorcycle_detail_candidates`
rows.

### Performance Notes

No extra inference: the reservation adds a lock acquire/release per job, batch,
or frame, and one cheap `SELECT COUNT(*)` per idle scan pass. A busy device now
costs a skipped batch instead of a crop pass.

### Known Limitations

- 39 pre-existing suite failures remain unrelated to this work (the
  `enforcer_client` + `test_db` fixture order drops the `users` table, so API
  tests 401). Identical before and after this change.
- Reviewer time and attribute precision/recall remain unmeasured; the labeled
  development evaluation set is still a missing gate.
- Nothing is activated: no model is promoted and no violation is created.

### Next Recommended Steps

Fix the fixture-order bug in `tests/conftest.py` (make `test_db` not re-drop
`users`, or seed the enforcer after the final `init_db`), then assemble the
labeled evaluation set.

### Completion Status

Status: ✅ Completed (regressions added; pre-existing failures unchanged)

## 2026-09-30 08:25 — Three-class motorcycle detail submodel contract and main-detector attribution

### Objective

Make the application ready for a separate three-class YOLOv8 motorcycle detail
model (`helmet_nut_shell`, `helmet_acceptable`, `side_mirror`) that scans the
queued motorcycle crops, while the main YOLOv8m/ByteTrack detector keeps its
15-class contract and remains the only source of rider and motorcycle
attribution. Detail output must stay review-only and never create or confirm a
violation. No training, weight designation, dataset change, or migration.

---

### Summary

The detail checkpoint gate now validates a dedicated three-class contract
(`0=helmet_nut_shell, 1=helmet_acceptable, 2=side_mirror`) instead of the main
15-class roster, and rejects the exploratory pilot order, the main checkpoint,
and malformed maps before any crop is scanned. The collector stores the main
detector's rider and nearby-motorcycle context per retained frame (additive
JSON, no schema change), and the scanner attributes helmets and mirrors against
that context so overlapping bikes stay ambiguous. The review page shows the
model identity, class map, mapped boxes, attribution source, and uncertainty.

### Detailed Changes

- **Class contract.** IDs must be contiguous from 0, exactly three, exact
  names, exact order. Rejection codes: `missing`, `malformed`,
  `non_contiguous_class_ids`, `duplicate_names`, `wrong_class_count`,
  `renamed_names`, `reordered_names`. Case/whitespace variants are rejected as
  renamed. The pilot order's reason says "exploratory pilot order; IDs are
  never relabeled". Order choice: the Sept 30 draft `data.yaml` declares
  `[helmet_nut_shell, helmet_acceptable, side_mirror]`.
- **Gate.** Failures keep rows `queued` with `scan_error=detail_class_map_rejected:<code>: <reason>`
  or `detail_checkpoint_wrong_task:<task>` and consume no attempt; zero crops
  are read. Verified read-only against real files: both Sept 30 YOLOv8n pilot
  `best.pt` files fail `reordered_names`; `models/tavidm_yolov8m.pt` fails
  `wrong_class_count`.
- **Main context.** Each retained frame gets `main_context`: target track,
  main rider state/box/track/reasons, up to 8 other main-detector
  `motorcycle`/`rider` boxes intersecting the crop (sorted by overlap,
  `truncated` flag). `person` is never stored.
- **Association.** Rider from main context only; ambiguous/missing rider leaves
  the helmet unknown. Helmets in another rider's head region and mirrors in
  another motorcycle's mounting area are left unattributed; an overlapping
  main-detector motorcycle (IoU >= 0.20) makes mirrors ambiguous.
- **Old rows.** Rows without `main_context` use stored `rider_bbox` or report
  the rider `unrecorded`, and add
  `context:nearby_motorcycles_not_recorded_for_this_row`. Older scans display
  "(older scan recorded before the three-class detail contract)".

---

`core/detection_config.py`, so the main and detail gates normalise maps the
same way while enforcing different rosters. Context is captured at collection
time because the main detector's detections are unavailable when the queued
scan runs later. Unchanged: frame selection bounds, occurrence dedup, one GPU
reservation per batch, checkpoint refresh on designation change, startup and
stale recovery, retry limits, and fail-closed behaviour.

### Code Impact

## 2026-09-30 08:50 — Motorcycle detail scan: fail closed on task metadata and incomplete context

### Objective

Close two fail-closed gaps in the three-class detail integration: (1) a
checkpoint with missing or invalid task metadata passed the gate when its class
names matched; (2) truncated saved context could still yield a definite helmet
or mirror attribution although an omitted neighbour might own it.

---

### Summary

The detail gate now accepts only an explicit `task == "detect"`, rejecting
missing, blank, non-string, and other task values before any crop is read or
any attempt is spent. Saved main-detector context records which neighbour list
was truncated, and helmet or mirror attribution becomes `ambiguous` whenever the
list that could own it is truncated or was never recorded. Complete context
keeps definite attribution.

---

### Files Modified

    `motorcycles_truncated` / `riders_truncated` (with `truncated`,

    `_stored_truncation`; `build_main_context` sets per-list flags;

---

### Detailed Changes

- Task gate reasons: `detail_checkpoint_task_missing` (None/blank),
  `detail_checkpoint_task_malformed:<type>` (non-string),
  `detail_checkpoint_wrong_task:<task>` (e.g. `classify`, `segment`). Checked
  before the class map; the three-class ID contract is unchanged.
- Stored context adds `truncated_lists: {"motorcycles", "riders"}`; the generic
  `truncated` flag is kept as "either list". Reading: a valid per-list boolean
  wins; otherwise the generic flag applies to both (v1 rows); if neither is a
  real boolean the list counts as truncated.
- A list is complete only when recorded and not truncated. Incomplete riders:
  a helmet in the head region is `ambiguous`
  (`nearby_rider_context_incomplete_helmet_unattributed`). Incomplete
  motorcycles: a mirror in the mounting area is `ambiguous`
  (`nearby_motorcycle_context_incomplete_mirror_unattributed`). With nothing
  observed the states stay `unknown` / `none_visible`.
- Rows without `main_context` now also count as incomplete (previously a stored
  `rider_bbox` allowed a definite helmet/mirror state) and gain
  `context:nearby_riders_not_recorded_for_this_row`.

---

### Technical Explanation

Truncation is evaluated per list because a helmet can only belong to a rider
and a mirror only to a motorcycle, so one truncated list should not erase the
other attribute. Completeness is a property of the stored context, so the
association functions stay pure and the legacy spatial path (no main context)
keeps its defaults.

---

### Code Impact

engine, queue states, routes, and RBAC are untouched.
