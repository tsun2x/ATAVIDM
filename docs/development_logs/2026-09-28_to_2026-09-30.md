## 2026-09-28 — Hybrid motorcycle detail-review workflow (implemented, not activated)

### Objective

Add a hybrid detail-review workflow for uploaded videos: group motorcycle
detections by track occurrence, keep at most two useful frames per occurrence,
run a queued second YOLOv8 pass over the padded crops, and present helmet and
side-mirror observations in a separate human-review queue — without ever
declaring, confirming, or creating a violation.

### Summary

New `core/motorcycle_detail.py` (selection + association) and
`core/motorcycle_detail_scan.py` (checkpoint gate + queued crop pass) were
wired into uploaded-video processing. A new additive table
`motorcycle_detail_candidates` (migration 011) stores one candidate per track
occurrence with its run-scoped evidence, scan state, observations, and human
outcome. New authenticated routes and a UI page expose the queue to enforcers.
The existing `review_queue`, its confirm/dismiss API, and the 12 canonical
violation types are unchanged, and the crop scan cannot reach the violation
engine.

### Files Modified

- `core/motorcycle_detail.py` (new) — occurrence registry, frame scoring,
  crop geometry, coordinate mapping, rider/helmet/mirror association, bounded
  collector.
- `core/motorcycle_detail_scan.py` (new) — designated-checkpoint gate, exact
  15-class validation, crop predictor, mapping/overlay, bounded resumable
  scanner.
- `core/evidence.py` — additive detail evidence writers
  (`save_detail_evidence`, `save_detail_overlay`, `remove_detail_run`).
- `core/video_processor.py` — collector hook on already-processed frames,
  run-scoped persistence, run-scoped cleanup on failure.
- `core/video_lifecycle.py` — retention for detail rows and run-scoped
  directories on remove-results, annotation invalidation, and permanent delete.
- `database/schema.sql`, `database/migrations/011_motorcycle_detail_review.sql`,
  `database/sqlite_adapter.py`, `database/db.py`, `database/adapter_base.py` —
  additive table, migration, and adapter surface.
- `app.py` — detail queue routes, scanner lifecycle, nav entry.
- `templates/motorcycle_detail_review.html`, `static/js/motorcycle_detail_review.js`
  (new) — review workspace with scene/crop/overlay views and outcome actions.
- `config.py`, `.env.example` — explicit detail-checkpoint designation and the
  collection toggle.
- `scripts/measure_motorcycle_detail.py` (new) — local prototype measurement.
- `docs/specs/2026-09-28-motorcycle-detail-review-design.md` (new) — design,
  annotation protocol, and missing evaluation-set gate.

### Files Created (tests)

### Database Changes

Additive only: one new table plus four indexes via
`database/migrations/011_motorcycle_detail_review.sql`. No existing table,
column, constraint, or index was altered, and the existing `review_queue`

### API Changes

New, additive, role-gated: `GET /motorcycle-detail-review`,
`GET /api/motorcycle-detail-review`,
`GET /api/motorcycle-detail-review/<id>/evidence/{scene,crop,overlay}`,
`POST /api/motorcycle-detail-review/<id>/outcome`,
`POST /api/motorcycle-detail-review/scan-now`. No confirm or case-creation
route exists on this queue.

### Performance Notes

Selection adds no inference: the collector only scores frames the pipeline
already produced. Numbers are in the completion report; reviewer time and
attribute precision/recall remain unmeasured because the labeled development
evaluation set is still a missing gate.

### Known Limitations

- Live-stream integration is deliberately deferred to a later phase.
- Without a designated 15-class detail checkpoint the crops stay `queued` with
  a visible reason (fail closed); no observation is produced.
- The selection weights, crop margins, and association thresholds are
  engineering heuristics, not validated thresholds.
- A candidate row is created per track occurrence; the two retained frames live
  in `frames_json` so a retry updates the same row.

## 2026-09-28 — Shared GPU reservation, occurrence bounds, and scan recovery

### Objective

Fix four review findings in the motorcycle detail workflow: a single shared GPU
reservation for every inference caller, motorcycle-only occurrence bounds,
spatial mirror attribution, and queued-scan/checkpoint-gate recovery after a
restart.

### Summary

`core/gpu_inference_slot.py` (new) is now the authoritative single-slot
reservation for the one GPU. The uploaded-video worker, background crop
batches, the manual `scan-now` batch, and every live camera frame take it in
turn, with strict priority (video job > crop batch > live frame) and FIFO within
a level. The video worker holds it for the whole job and re-queues at the queue
head when its bounded wait elapses; live frames never wait and are dropped.
`TrackOccurrenceRegistry` now bounds motorcycle and non-motorcycle occurrences
separately, so a frame of 24 cars can no longer evict the motorcycle under
review. Mirror attribution matches the target by spatial IoU, so a padded crop
re-detecting its own motorcycle is no longer mistaken for a second, overlapping
bike. The scanner refreshes a failed checkpoint gate by configuration
fingerprint, skips a batch without claiming when the device is busy, and
recovers `scanning` rows abandoned by a dead process at start-up. That
start-up recovery strictly precedes the scanner thread, and a broader
start-up pass is still permitted after an early stale-only pass, so the loop's
first batch can no longer consume the one-shot recovery and strand a row that a
just-dead process abandoned inside the stale window.

### Files Modified

- `core/gpu_inference_slot.py` (new) — priority/FIFO reservation with bounded
  waits, same-owner reentrancy, and introspection.
- `core/motorcycle_detail.py` — separate `max_active` / `max_foreign` budgets,
  bounded generation bookkeeping, spatial target matching for mirrors.
- `core/motorcycle_detail_scan.py` — reservation-bounded batches, queue peek
  before claim, checkpoint fingerprint + model cache stamp, start-up recovery.
- `app.py` — worker reservation, `_gpu_slot`, `_VIDEO_JOB_GPU_WAIT_SEC`,
  `_background_workers_allowed`, `bootstrap_detail_queue`, first-request
  bootstrap, manual `scan-now` 409 on a busy device.
- `core/live_stream.py` — per-frame non-blocking reservation with dropped-frame
  accounting.
- `database/sqlite_adapter.py`, `database/db.py`, `database/adapter_base.py` —
  `recover_stale_motorcycle_detail_scans(..., include_recent=False)` and
  `count_queued_motorcycle_detail_scans()`.

### Files Created (tests)

- `tests/test_gpu_inference_slot.py` — mutual exclusion, preemption, non-blocking
  live frames, release on exception, idempotent release, 10-thread contention.
- `tests/test_gpu_reservation_wiring.py` — video job holds and returns the
  device, release on failure, re-queue on timeout, bootstrap idempotency,
  reloader-parent opt-out, manual 409, live-frame drop.

### Database Changes

None. No table, column, index, or migration was added or altered; the two new
adapter methods read and update the existing `motorcycle_detail_candidates`
rows.

### Performance Notes

No extra inference: the reservation adds a lock acquire/release per job, batch,
or frame, and one cheap `SELECT COUNT(*)` per idle scan pass. A busy device now
costs a skipped batch instead of a crop pass.

  tests 401). Identical before and after this change.
- Reviewer time and attribute precision/recall remain unmeasured; the labeled

- Nothing is activated: no model is promoted and no violation is created.
