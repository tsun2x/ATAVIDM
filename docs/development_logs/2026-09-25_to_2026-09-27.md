## 2026-09-25 23:52 — Security and list-loading audit fixes

### Objective

Implement the previously audited TAVIDM frontend/backend fixes: secure authentication defaults and private file handling, prevent stored XSS, expose all records through pagination, avoid report filename collisions, return JSON authentication errors to API clients, and document the processing queue's single-process requirement.

### Summary

Replaced the hard-coded Flask signing key with a random development key and production configuration requirement. Removed the default admin password path; first-time or legacy-default admin setup now requires an explicit 12-character bootstrap password. Sessions revalidate account activity, current role, and password state from the database. Evidence and reports now use authenticated serving routes, with previous `static/evidence` and `static/reports` files still supported through those routes. The violations screen now queries paged records from SQLite; review queue pages expose totals and navigation. Dynamic values in reports, settings, violations, and review evidence views are escaped or assigned as text.

### Detailed Changes

- Authentication now trusts current database account status and role instead of stale cookie fields. Changing the password invalidates previously issued sessions.
- `FLASK_SECRET_KEY` is mandatory in production. Development creates a random key if none is configured. `TAVIDM_BOOTSTRAP_ADMIN_PASSWORD` is required when creating the admin account or replacing the old `admin123` credential.
- Existing files under the legacy static directories are not moved or deleted. Direct static URLs return 404; authorized evidence and report routes resolve paths only under configured or legacy allowlisted roots.
- Report output filenames include a UUID suffix to avoid same-second collisions.
- The violations page and review queue use bounded database pagination. Search still supports IDs, violation types, source filenames, track IDs, and reason text.
- Report history, zone-template fields, violation rows, and evidence detail values no longer insert unescaped database strings into HTML.
- The in-memory processing queue remains single-process; README now states that multiple WSGI worker processes would have separate queues and could process concurrently.

### Performance Notes

Violation records are fetched a page at a time instead of materializing up to 1,000 rows at page load. Each server request is capped at 100 rows.

### Known Limitations

The video-processing queue remains in memory and requires one WSGI worker process. Development signing keys are regenerated at process start unless `FLASK_SECRET_KEY` is configured, which invalidates old sessions on restart.

### Risks

First launch, or startup with the legacy `admin/admin123` account, now stops until `TAVIDM_BOOTSTRAP_ADMIN_PASSWORD` is set. Production startup also requires a stable `FLASK_SECRET_KEY`. These settings are documented in the README.
