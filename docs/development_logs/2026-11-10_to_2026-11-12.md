## 2026-11-12 00:07 — Preserve CCTV scene drafts and stream lifecycle

### Objective

Run the saved `cctv 1 fix` implementation prompt: preserve camera annotation edits across navigation, clarify stream-worker lifecycle, and support deliberate scene copying between camera and video annotation through zone templates.

### Summary

Added account- and source-scoped browser draft storage for camera and video annotations, with explicit recover/discard choice, stale-server-scene warning, and storage failure notice. Added full-scene template copy controls in the shared editor and the option to save a camera scene plus a reusable template copy. Stream workers remain independent of viewer connections; manager behavior now retains a stopping worker until it exits, reports `stopping`, and refuses to start an overlapping worker.

- `tests/test_live_camera_annotation.py` — verifies stale camera-scene saves return a conflict without overwriting the newer scene.

### Detailed Changes

- Draft keys include account ID, source kind and source ID. Draft values retain the full scene plus the server scene used as their baseline. A stale baseline prompts before recovery; choosing Cancel discards the stored draft and opens the current server scene.
- Drafts clear after confirmed camera/video save or explicit discard. Browser storage errors are surfaced to the user. Unscoped legacy browser keys are left untouched because they have no account ownership metadata.
- Camera saves include the scene baseline and the existing PUT route returns HTTP 409 if another update changed the stored scene since the editor loaded. The route accepts the new baseline field optionally, preserving existing clients.
- The scene editor can copy the complete scene document from a selected template for either a camera or a video. The UI confirms the copy and reminds the operator to compare geometry with the target reference frame. Camera edits can save both the camera scene and a new template snapshot.
- A stop request no longer removes a still-running worker from the manager registry. Repeated start requests reuse it while it is stopping, and status polling reports `stopping`; a new worker can start once the old thread exits.

### Technical Explanation

The implementation reuses the existing zone-template endpoints and scene-document parser, so template reuse remains a detached copy and preserves supported scene fields. Browser drafts are local to the authenticated account and source. The stream manager's existing lock serializes worker replacement; retaining a worker until `is_alive()` becomes false prevents overlapping pipelines for one camera while a capture read unwinds.

## 2026-11-12 01:23 — Fix camera save/reconnect and scene/template races

### Objective

Run the saved `4 fix cctv` prompt addressing reconnect races, atomic camera-scene saves, account ownership of browser drafts, and camera-template list refresh.

### Summary

Camera saves now schedule a bounded background worker replacement. The stopping worker stays registered until exit, explicit Stop cancels a pending replacement, status polling drives bounded frontend reattachment, and timeout/error states are visible. Camera scene expected-value comparison and update now happen within one SQLite write transaction. The browser never reads or deletes the old unscoped draft key. Newly created camera templates are inserted into both template lists immediately and refreshed from the server; retry after a partial camera-save failure reuses the existing template.

### Performance Notes

No new inference work or workers are created by navigation. A worker in its stop transition is retained briefly to prevent overlap; a new stream request during that transition may show `stopping` until the existing capture loop exits.

### Known Limitations

Browser drafts are device/browser-local and do not sync across devices. Reusing geometry assumes matching viewpoint and framing. Real-camera annotation recovery, template alignment, reconnect timing, and RTSP failure behavior were not manually verified.

### Risks

If camera template creation succeeds but the subsequent camera save fails, the reusable template remains created and the UI reports the partial outcome; the camera draft remains available for recovery.
